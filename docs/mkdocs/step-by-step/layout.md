# Hypline dataset layout

Hypline's fMRI workflow starts with data already preprocessed with
fMRIPrep. This guide assumes some familiarity
with its BIDS organization: subjects (`sub-*`), optional sessions (`ses-*`),
and functional runs stored under `func/`. Hypline reads the preprocessed BOLD
data and confound files from `derivatives/fmriprep/`; it does not run fMRIPrep
or require the original raw BOLD images.

Each data-processing command takes the **dataset root** as its main positional argument.
You organize files according to hypline's conventions so that commands can find their 
inputs and write outputs without separate paths for every file.

We will explain how to prepare your data for hypline in three steps.

1. Overview. This page explains the data structure: how hypline organizes subject-level
   brain data and dyad-level conversation data.
2. Create. The second step reviews the files necessary for running hypline, including how to label meaningful segments of your data and provide metadata files. See [Segments and metadata](segments.md).
3. Organize. To assemble your own data, files, and metadata files in the standardized hypline format,
   see [Prepare your own dataset](prepare-dataset.md).

Once your dataset is
ready, continue to the command-specific guides, beginning with [hypline transcribe](transcribe.md).


## The root tree

A hypline dataset extends the [BIDS](https://bids.neuroimaging.io/) structure with
directories for conversation data and analysis outputs. The tree below shows both inputs and outputs;
hypline creates the output directories as you run the corresponding commands.

```text
<dataset-root>/
├── participants.tsv                         # required: dyad ↔ subject mapping
├── sub-041/ses-1/func/                      # events files you provide (you can also store raw BIDS here)
├── derivatives/
│   ├── fmriprep/sub-041/ses-1/func/         # fMRIPrep outputs (preprocessed BOLD)
│   └── hypline/sub-041/ses-1/func/          # hypline imaging derivatives (denoised BOLD)
├── stimuli/dyad-040/ses-1/
│   ├── audio/                               # audio files you provide
│   └── transcript/                          # generated transcripts
├── features/dyad-040/ses-1/phonemic/        # generated features
├── confounds/dyad-040/ses-1/phonemic/       # generated confounds
├── results/sub-041/
│   ├── encodingModel-v1/                    # fitted encoding models
│   └── encodingEval-v1/                     # evaluation results
├── nuisance/sub-041/ses-1/physio-v1/        # nuisance regressors you provide (optional)
└── logs/<command>/                          # per-ID run logs, written by every command
```

| Source        | Files or directories   | Description             |
| ------------- | ------------- | ------------------------------- |
| You provide  | `participants.tsv`   | Maps each subject to a dyad. |
| You provide   | `sub-*/[ses-*]/func/*_events.tsv`   | Describes the timing and labels of events within each run.   |
| fMRIPrep generates; you provide   | `derivatives/fmriprep/`  | Preprocessed BOLD data and fMRIPrep confound files. |
| Hypline generates | `derivatives/hypline/`    | Denoised BOLD data, generated by [`denoise`](denoise.md) ). |
| You provide   | `stimuli/dyad-*/[ses-*]/audio/`   | Conversation recordings per dyad. |
| Hypline generates | `stimuli/dyad-*/[ses-*]/transcript/`   | Transcripts of the recordings.   |
| Hypline generates, or you provide | `features/` and `confounds/`   | Stimulus features and their associated confounds. |
| Hypline generates | `results/`    | Fitted encoding models and evaluation results. |
| You provide (optional)   | `nuisance/`  | Additional subject-level nuisance regressors, such as physiological recordings. |
| Hypline generates | `logs/`    | Per-subject or per-dyad logs for each command. |

You must supply the **`*_events.tsv` files**; hypline does not generate them.
Each file is a tab-separated table describing the timing and labels of events
within a run. See [Segments and metadata](segments.md) for the required columns
and conventions.

The **`derivatives/hypline/`** tree mirrors fMRIPrep's
`sub-XX/[ses-YY/]func/` organization and carries its own
`dataset_description.json`.

The optional regressors under **`nuisance/`** are used by
[`denoise`](denoise.md) alongside fMRIPrep's confounds. These differ from the
stimulus confounds under **`confounds/`**, which are used in encoding analyses.


!!! info "Sessions are optional"

    Examples here use a `ses-1/` level under each subject
    (`sub-041/ses-1/func/`) to match the tutorial dataset. Datasets without
    sessions omit the level entirely (`sub-041/func/`). Hypline handles both cases.

## Subject vs. Dyad

Hypline organizes files by either the individual participant or the shared
conversation:

- **`sub`-keyed** — assiciated with one participant: brain data (`derivatives/fmriprep/`,
  `derivatives/hypline/`), events files, additional nuisance regressors (`nuisance/`),
  and encoding results (`results/`). Each partner has their own BOLD data and fitted encoding model.
- **`dyad`-keyed** — derived from the *shared conversation* between two partners:
  recordings and transcripts (`stimuli/`), stimulus features (`features/`), and stimulus confounds (`confounds/`).
  Each dyadic conversation run has one shared set that can be used to fit a separate encoding model
  for each partner. A `dyad-040` audio file represents the shared recording.

You connect these identifiers through **`participants.tsv`**, a standard BIDS table at 
the dataset root. Alongside its `participant_id` column, add a custom **`dyad_id`** column:

```tsv
participant_id   dyad_id
sub-041          dyad-040
sub-042          dyad-040
```

Here subjects `041` and `042` are partners in `dyad-040`. When fitting an encoding
model for `sub-041`, hypline looks up that subject's dyad in this table and reads the 
features for `dyad-040`. This is the only way hypline knows which subjects make up 
which dyad. Matching subject and dyad numbers is not enough!

You need this table whenever a command connects subject-level brain data to dyad-level
conversation data. A workflow that uses only subject-level files, such as running `denoise`
alone, does not require it.


## File-naming convention

Hypline follows BIDS filename conventions: `entity-value` pairs 
are joined by underscores (`_`), followed by a suffix and extension.
For example:

```text
sub-041_task-conv_run-1_space-T1w_desc-preproc_bold.nii.gz
\____________________________________________/ \__/ \_____/
                   entities                   suffix   ext
```

A filename begins with either `sub` or `dyad`. For run-level files, `ses`
(when present), `task`, and `run` identify the session, task, and run. Generated
run-level files retain these identifiers from their source files.


### Category entities

Files stored under `features/`, `confounds/`, `nuisance/`, and `results/`
also carry a **category entity** that identifies their contents:

| Entity        | Area          | Example                         |
| ------------- | ------------- | ------------------------------- |
| `feat-<kind>`   | `features/`   | `feat-phonemic`, `feat-semantic`, `feat-spectral`, `feat-syntactic` |
| `conf-<kind>`   | `confounds/`  | `conf-phonemic`, `conf-semantic` |
| `nuis-<kind>`   | `nuisance/`   | `nuis-physio`                   |
| `result-<kind>` | `results/`    | `result-encodingModel`, `result-encodingEval` |

The `<kind>` determines the subdirectory. For example, a phonemic feature
(`feat-phonemic`) lives under `features/dyad-040/ses-1/phonemic/`. 

Denoised BOLD files under `derivatives/hypline/` instead follow standard
BIDS-derivatives naming and use `desc-denoised`.

Recordings and transcripts use a filename suffix (`_audio` or `_transcript`)
instead of a category entity. For example,
`dyad-040_ses-1_task-conv_run-1_audio.wav` lives under
`stimuli/dyad-040/ses-1/audio/`.

### `desc` variants

Some commands accept a `--desc` label that tags an output as one *variant* among
several. Variants live in their own subdirectory so they stay physically
separate:

```text
confounds/dyad-040/ses-1/
├── phonemic-onset/    # conf-phonemic_desc-onset — speech-onset indicator
└── phonemic-rate/     # conf-phonemic_desc-rate  — speech rate per TR
```

Similarly, `result-encodingModel_desc-v1` is stored under
`results/sub-041/encodingModel-v1/`. These directories let you keep multiple
variants and select the one you want by name.

## Why the convention matters

A standard naming and file structure convention means commands compose cleanly: each
reads what earlier steps wrote, with no configuration file wiring inputs to
outputs. It also keeps your dataset self-describing, since the directory tree itself
records what has been generated and from what.
